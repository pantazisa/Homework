\begin{abstract}
This report presents an MD5 password-recovery tool formulated as an \textbf{A* state-space search}
over a prefix tree and parallelized across five paradigms: POSIX threads, OpenMP, OpenCilk,
CUDA, and a Hybrid Pthreads\,+\,CUDA design. The search uses a uniform cost model over a fixed
76-symbol alphabet with a bounded beam to cap memory. We describe the algorithmic formulation,
the parallelization strategy of each implementation, and an experimental evaluation on a 28-core
host equipped with an NVIDIA GeForce RTX~4070~Ti~SUPER. All implementations recover length-4
targets correctly; the Hybrid design additionally succeeds on the harder length-5 space where the
CPU-only variants exhaust their search budget.
\end{abstract}

% ==================================================================
\section{Problem Formulation}
% ==================================================================
Given the MD5 digest of an unknown password of known length $L$, the goal is to recover the
plaintext. Because cryptographic hashes exhibit the \emph{avalanche effect}, there is no continuous
notion of ``distance'' between a partial candidate's hash and the target. We therefore do not use
the hash to guide the search; instead we treat the problem as a graph search over a prefix tree and
use A* as a systematic, memory-bounded traversal.

\paragraph{State-space model.}
\begin{itemize}[nosep]
  \item \textbf{State:} a candidate prefix string $s$ at depth $d$.
  \item \textbf{Alphabet:} a fixed 76-symbol set --- lowercase, uppercase, digits, and the symbols
        \verb|!@#$%^&*()-_=+|.
  \item \textbf{Path cost:} $g(n) = d \cdot \text{EDGE\_COST}$, with $\text{EDGE\_COST}=1.0$.
  \item \textbf{Heuristic:} $h(n) = (L - d)\cdot \text{EDGE\_COST}$ (remaining depth; admissible).
  \item \textbf{Evaluation:} $f(n) = g(n) + h(n) = L$, uniform across all candidates of the target
        length.
  \item \textbf{Goal test:} MD5 verification is performed \emph{only} when a candidate reaches
        depth $L$ (a leaf).
\end{itemize}

Since $f$ is uniform, A* here behaves as a systematic frontier expansion. To bound memory we apply
\textbf{beam trimming}: when the priority queue exceeds \texttt{BEAM\_CAP} $=3\,000\,000$ states, a
\texttt{quickselect} keeps the best \texttt{BEAM\_KEEP} $=1\,200\,000$ and re-heapifies. There is
\textbf{no brute-force fallback and no training} of any kind: a case reported as \emph{not found} is
a genuine failure within the search's own node/time budget.

\paragraph{Priority queue.} A binary min-heap ordered by $f$ supports \texttt{push} and \texttt{pop}
in $O(\log n)$. Beam trimming uses \texttt{quickselect} to partition the best $k$ states in expected
$O(n)$ before re-heapifying, avoiding a full $O(n\log n)$ sort.

% ==================================================================
\section{Parallelization Strategies}
% ==================================================================

\subsection{Pthreads}
The root search space is partitioned into two-character prefix tasks ($76^2 = 5\,776$ independent
sub-searches for $L\ge 2$). Worker threads claim tasks dynamically through an atomic counter
(\texttt{atomic\_fetch\_add}), which provides natural load balancing. Each thread owns a
\emph{private} priority queue, eliminating lock contention on the heap. An atomic flag signals early
termination the moment any thread finds the match.

\subsection{OpenMP}
Uses the same 5\,776-task decomposition, distributed with
\lstinline|#pragma omp parallel for schedule(dynamic, 1)|. A per-thread queue is preallocated and
reused (indexed by \texttt{omp\_get\_thread\_num()}) to avoid repeated heap allocation.

\subsection{OpenCilk}
Exposes the sub-tasks to the work-stealing runtime with \texttt{cilk\_for}; each iteration runs an
independent A* traversal with its own local heap. Worker count is controlled via
\texttt{CILK\_NWORKERS} or \texttt{--threads}.

\subsection{CUDA}
The CPU performs the pointer-based traversal and heap operations while completed leaf candidates
accumulate in a batch buffer. When the batch fills (or a node threshold is reached) the candidates
are copied to the GPU and hashed in parallel by an optimized MD5 kernel. Here \texttt{--threads}
denotes the GPU \emph{batch size}, not a CPU thread count.

\subsection{Hybrid Pthreads + CUDA}
Combines CPU dynamic task distribution with GPU batch execution. Each POSIX worker is assigned
(i)~its own CUDA stream (\texttt{cudaStreamCreate}) for concurrent GPU execution, (ii)~pinned host
memory (\texttt{cudaHostAlloc}) for DMA transfers, and (iii)~private device buffers/flags to avoid
device-side synchronization.

\section{Discussion}
% ==================================================================
\begin{itemize}[nosep]
  \item \textbf{Decomposition quality.} The 5\,776 two-character prefix tasks give plenty of
        parallel slack for a 28-core host, and per-thread private heaps remove the main contention
        point, which is why Pthreads scales near-ideally to 8 threads.
  \item \textbf{Runtime differences.} OpenMP is consistently a bit slower than Pthreads at the same
        thread count due to scheduling overhead. OpenCilk wins at low thread counts but its
        work-stealing makes the number of expanded nodes --- and therefore time --- less predictable.
  \item \textbf{GPU trade-off.} Pure CUDA rarely beats a well-parallelized CPU at length~4 because
        the bottleneck is CPU-side frontier expansion, not hashing. The GPU only pays off when the
        leaf-verification volume is large, which is exactly the length-5 regime.
  \item \textbf{Batch size matters.} For the Hybrid design, small batches ($16\,384$) drown in
        kernel-launch overhead; batches of $262\,144$--$1\,048\,576$ minimize launches and give the
        best time.
  \item \textbf{Oversubscription.} At 32 threads several Hybrid cases show a jump in node count and
        time --- contention for the single GPU plus frontier divergence outweighs added CPU parallelism.
\end{itemize}

\section{Conclusion}
% ==================================================================
All six implementations are correct and reproducible. On length-4 targets the CPU parallel variants
achieve near-ideal speedups (Pthreads reaches $\approx 22\times$ at 32 threads), while pure GPU
offloading is limited by CPU-side frontier expansion. The decisive result is at length~5: only the
Hybrid Pthreads\,+\,CUDA design, combining dynamic CPU task distribution with per-thread CUDA
streams and large GPU batches, extends the reach of the search into a space where every CPU-only
implementation fails. This confirms that heterogeneous CPU+GPU cooperation --- not GPU offloading
alone --- is what unlocks the harder search regime.
